# 今日事项 · 习惯 · 目标 —— 连接与关系评估及改进方案

> **评估对象**：有秋（Yield）v1.3.0 + 工作区未提交改动（`main` 分支，HEAD `878cbe1`）
> **评估时间**：2026-10-20
> **评估范围**：今日事项（今日页 / DayBoard）、习惯（HabitsView / habit_checks）、目标（GrowthView / goals / goal_entries）三者的连接与关系
> **方法**：代码与数据模型审阅 + 关键链路逐行核对 + 测试基线（`npx vitest run`：30 文件 / 208 用例全绿）
> **相关文档**：[README](../README.md)、[ARCHITECTURE](ARCHITECTURE.md)、[PRODUCT_REVIEW](PRODUCT_REVIEW.md)、[CHANGES](CHANGES.md)
>
> **方案修订记录**
> - **v2（2026-10-20）**：依据产品定位补充重写方案。定位澄清为「**目标 = 里程碑式的长期最终结果；重复性归习惯；任务是一次性行动**」。
>   - 目标不再承载任何周口径与"贡献计数"，改为**判据化**（数值/次数、阶段、项目）。

> - **v1（2026-10-20）**：初版评估与改进方案。

## 0. 一句话结论

三者之间是**三根各自独立的水管接进同一个水槽**：数据层有两条进料通道（任务 → 目标、习惯 → 目标），都写进 `goal_entries`；展示层把任务与习惯并排成今日页的一张清单、把目标压成一条 `GoalStrip`。

真正缺的不是"连接"，而是三样东西：

1. **口径一致性** —— 同一屏会出现两个分母（`effectiveWeeklyTarget` vs `goal.weekly_target`），frequency 目标的分子含任务而分母只算习惯，project 型目标在今日条上显示成 `45/1%`。
2. **关系** —— 任务与习惯互不相识（schema 里没有关联字段），目标与事项之间没有反向索引，"同一件事"可以被记两次账。
3. **共同的节拍器** —— 目标只有"累计"一种口径真正生效（`weekly_target` 是死字段），习惯只有"每周几次"没有"周几做"，今日页因此无法回答"今天该做什么、在推进什么"。

**北极星原则**（后续所有设计围绕这两句）：

> ① 一个行动，只对一个目标记一次账。
> ② 今天的每一件事，都能说出它在推进什么。

**v2 补充的三条边界**（依据产品定位澄清，见 §3.0）：

> ③ 任务是"做"（一次性），习惯是"保持"（重复），目标是"到达"（有终点的最终结果）。
> ④ 凡是"每周 N 次"都归习惯；目标不承载任何周期口径。
> ⑤ 一个动作与目标的关系分两种：**计量**（算目标的一个单位）与**服务**（只作上下文），由用户显式声明，默认服务。

## 2. 不足之处

### A 级：口径错乱 —— 数字不可信

> 这一组最要命：它让"目标"在用户眼里从"可参照的刻度"退化成"一个会动的数字"，而用户恰恰要靠它决定今天做什么。

#### A1. `weekly_target` 对 quantity 目标**完全无效**，但界面上它像一个有效设置

- **证据**：
  - `src/components/GrowthView.tsx:306` — `formShowsWeekly = goalKind === "quantity" || goalKind === "frequency"`，quantity 目标也显示「每周目标次数」输入框；
  - `src/components/GrowthView.tsx:230` — 保存进 `values.weekly_target`；
  - `src/components/GrowthView.tsx:549` — 目标卡脚注还把它当文案回显：`每周 ${goal.weekly_target}${goal.unit}`；
  - `src/lib/db/growth.ts` `refreshGoalProgressOn` — quantity 走 `else` 分支：`current = start_value + SUM(goal_entries)`，**全程不读 `weekly_target`**；
  - `src/lib/growth.ts:32` — `calculateGoalProgress` 只在 `goal_type === "frequency"` 时读它。
- **后果**：用户填「每周 2 本」，界面回显「每周 2 次」，实际进度是无限累计。**看起来接上了，其实根本没接。**
- **影响面**：`weekly_target` 目前的唯一实际作用是 `frequency` 目标，而 `frequency` 目标在当前 UI 下无法创建（见 C1）—— 即这个字段**当前 100% 是死字段**。

#### A2. frequency 目标的分子含任务贡献，分母只算习惯贡献

- **证据**：`src/lib/db/growth.ts` `refreshGoalProgressOn` 的 frequency 分支：
  ```sql
  SELECT SUM(value) AS total FROM goal_entries WHERE goal_id=$1 AND entry_date >= $2
  ```
  **不限 `source_type`** —— 任务完成与习惯打卡一起计入周次数；而分母 `effectiveWeeklyTarget`（`src/lib/growth.ts:47`）在"单习惯驱动"时返回 `习惯每周次数 × 习惯贡献值`，**只含习惯**。
- **后果**：一个习惯驱动的 frequency 目标若同时关联了任务（`CreateTaskDialog` 的 `contributionGoals` 包含 frequency 目标，允许关联），显示形如 `5/3`。
- **同类问题**：`goalAcceptsSource`（`src/lib/growth.ts:4`）允许 quantity/frequency 接受 `task` 与 `habit` 两种来源，但没有去重规则 —— 任务与习惯指向同一件事时各记一笔。

#### A3. 同一屏出现两个分母

- **证据**：`src/components/today/GoalStrip.tsx:46` 数字用 `effectiveWeeklyTarget(goal, habits) || goal.weekly_target`，`GoalStrip.tsx:74` 进度条用 `calculateGoalProgress(goal)`，而后者内部读的是 `goal.weekly_target`（`src/lib/growth.ts:32-33`）。
- **背景**：工作区新增的 `effectiveWeeklyTarget`（`src/lib/growth.ts:47-64`）只改了**分母**的取法，`calculateGoalProgress` **没有同步更新**。
- **后果**：习惯「每周 2 次」+ 目标周目标 3 → 数字 `4/2`（200%），进度条 `4/3`（100%）。用户同时看到两个互相矛盾的数。

#### A4. project 型目标在今日目标条上是 `45/1%`

- **证据**：`GoalStrip.tsx:45-47` 对所有 active 目标一律用 `goal.target_value` 当分母；而 project 型的 `current_value` 是项目任务完成率百分比（0–100，`growth.ts` 的 `goal.goal_type === "project"` 分支），`target_value` 默认 1（`createGoal` 的 `Math.max(1, ...)`）。
- **后果**：数字在数学上不成立；进度条 `45/1` 被截断成 100%。

#### A5. 复盘页同页两处"目标"统计口径不一致

- **证据**：
  - 「长期目标投入」（`src/components/ReviewView.tsx:157-163`）—— 对 `goal_entries` 求和，**含 task + habit + manual**；
  - 「精力投向 → 按目标」（`src/components/ReviewView.tsx:55` → `aggregateReviewByGoal` in `src/lib/review.ts:63`）—— **只数任务**。
- **后果**：同一页、同一周，一个说"投入 12 次"，另一个说"完成 3/5 任务"。用户无法对账，也无从判断自己的习惯到底有没有被算进去。

#### A6. 成长热点图按目标筛选时，只筛了手动记录那一半

- **证据**：`src/components/GrowthView.tsx:141-143` 的 `visibleEntries` 受 `filterGoalId` 约束；但 `completedTasksByDate`（:153）与 `habitChecksByDate`（:172）**完全不受约束**。
- **后果**：选"只看目标 X"，热点图上仍亮着其它目标贡献的任务与习惯；筛选名不副实。

### B 级：关系缺失 —— 想连连不上

#### B1. 习惯没有"星期"，今日清单被 7 天全量污染

- **证据**：`habits` 表只有 `target_per_week`（每周几次），没有"周几做"。`src/components/today/DayBoard.tsx:65-68` 的注释已明说：
  > 今日事项把习惯一并列出（任务 + 习惯）；习惯模型只按每周次数设目标，没有星期字段，因此活跃习惯每天都出现在今日清单里。
- **后果**：
  - 「每周 3 次」的习惯在 7 天里全部出现，「每周 1 次」和「每周 5 次」在清单里长得一模一样；
  - 今日事项因此无法回答"**今天**该做什么" —— 这是整个闭环的地基塌陷点；
  - 用户要靠肉眼判断"这个我今天已经做过了"，而数据上做不到。

#### B2. 目标 → 事项没有反向索引

- **证据**：目标详情页（`src/components/GrowthView.tsx:388-424`）只有 hero、进度条、状态管理按钮。**看不到"正在推进这个目标的任务"，也看不到"贡献这个目标的习惯"。**
- **后果**：GoalStrip 的「推进」只能新建一张**空白任务**，用户得自己再填内容。目标与任务之间是"一次性的"，不是"持续的"。

#### B3. 任务 ↔ 习惯之间没有关系，同一件事会被记两次

- **证据**：schema 中 `tasks` 无 `habit_id`；`src/types/index.ts` 的 `Task` 无该字段。
- **后果**：完成"跑步 3 公里"的任务不会给"每日跑步"习惯打卡；反过来打卡也不会关掉那个任务。若两者都关联同一个 quantity 目标，**该目标当天 +2**，而用户只做了一件事。

#### B4. 今日事项不能按目标筛选或分组

- **证据**：`TodayAgenda` 的行模型是 `{kind:'task'} | {kind:'habit'}` 的平铺数组（`src/components/today/TodayAgenda.tsx`），只有行内一个 `.goal-chip` 小徽标。
- **后果**：用户在 20 条事项里无法一眼看出"今天哪几件事在推进我的目标"。**连接存在于数据层，却没有出现在视觉层。**

#### B5. 习惯行不能拖动

- **证据**：`TodayAgenda` 的 `SortableContext items={tasks.filter(isActiveTask).map(t => t.id)}` 只含任务 id；`onDragEnd` 只处理任务。
- **后果**：代码注释说今日是"one flat list"，实际上习惯被永久钉在清单顶部，且无法把任务拖到习惯之前。

### C 级：闭环断裂与激活不足

#### C1. 目标类型在 UI 里已经锁死为 `quantity`，刚落地的机制全部走不到

- **证据**（工作区未提交改动 `git diff src/components/GrowthView.tsx`）：
  - `GOAL_TYPES` 选择器被删除，`goalType` 状态被 `goalKind` 取代（由既有目标的 `goal_type` 推导）；
  - 新建时硬编码 `goal_type: "quantity"`（`GrowthView.tsx:247`）；编辑时 `setGoalKind(goal.goal_type)`，**界面无任何入口可改类型**。
- **后果**：`frequency` / `change` / `project` / `custom` 四种类型**在当前 UI 下无法创建**。于是：
  - `effectiveWeeklyTarget`（只对 frequency 生效）—— 死代码；
  - `habitDrivenWeekly`（要求 `goalKind === "frequency"`）—— 恒为 null，「每周目标次数由习惯决定」的提示 —— 永不出现；
  - 「每周目标次数」输入框对 quantity 恒定可编辑（因为 `habitDrivenWeekly` 恒 null）—— 存下一个没人用的值（回到 A1）。
- **判断**：把频率型语义并入累计型（"重复动作交给习惯"）本身是合理的产品收敛，但**配套的算法与提示没有一起收敛**，于是留下一地"看起来支持、实际走不到"的分支。这正是本次要修的根。

#### C2. frequency 目标没有终点

- **证据**：`refreshGoalProgressOn` 中 `reached` 对 frequency 恒为 `false`。
- **后果**：frequency 目标永不"已完成"、**永不生成成就**、无法自然归档；而 `goalAcceptsSource` 又要求 `status === 'active'`，一旦手动归档，该目标就彻底哑掉。

#### C3. 目标与"今天做什么"无关

- **证据**：`GoalStrip` 每行只有：标题、`current/target`、进度条、「推进」按钮。
- **后果**：目标只是"贴在今日页上方的一块进度"，没有回答"这个目标今天还差多少 → 我今天该做哪一件"。用户需要自己把目标翻译成动作 —— 而这正是产品该替用户做的那一步。

#### C4. 建成后未被激活

- **证据**：`docs/PRODUCT_REVIEW.md` §2.3 —— 成长目标 0 个 / 目标记录 0 / 目标里程碑 0，习惯 1 个、打卡 0 次。首启引导 `src/components/OnboardingGuide.tsx` 三步只讲"积微 / 有恒 / 提醒"，**没有一句教用户"目标 ← 任务 + 习惯"怎么连**。
- **后果**：任何新加的连接能力，如果没有**今日页上的自然入口**与**首启的一次具体示范**，大概率继续零使用。`GoalStrip` 这块新界面正处在这个风险上。

## 2.5 新模型如何消化旧发现

产品定位澄清后（目标 = 里程碑式最终结果；重复性归习惯），原方案里"目标靠任务/习惯自动计数"的整套记账机制被推翻。下表说明每条旧发现在新模型下的处置：

| 旧发现 | 新模型下的处置 |
| --- | --- |
| A1 `weekly_target` 是死字段 | **根除**。周口径整体移出目标，归习惯 |
| A2 frequency 分子含任务、分母只算习惯 | **根除**。frequency 目标类型取消 |
| A3 同一屏两个分母 | **根除**。目标只按"判据"算分母，只有一处 |
| A4 project 目标显示 45/1% | **根除**。项目型目标取消，项目降级为关联对象（3.1.2 / 决策 3） |
| A5 复盘页两处目标口径打架 | **保留修复**。统一为"判据推进"与"服务关系"两条明确的线 |
| A6 热点图按目标筛选只筛一半 | **保留修复**。筛选需按"服务关系"过滤任务与习惯 |
| B1 习惯没有"星期" | **保留并升级**。习惯接管重复能力，必须有排期 |
| B2 目标无反向索引 | **保留**。目标详情页「正在推进」区块 |
| B3 任务↔习惯无关系 | **不再需要 `tasks.habit_id`**。重复场景一律走习惯，任务不再重复 |
| （新增）同一动作被目标与习惯各记一次 | **根除**。关联三态 + 一个动作至多计量一个目标（3.4） |
| B4 今日不能按目标筛选/分组 | **保留**（降级为 P2，可选） |
| B5 习惯行不能拖动 | **保留**（小项） |
| C1 目标类型 UI 锁死为 quantity | **根除**。UI 继续不暴露类型，内部改为"判据"而非"类型" |
| C2 frequency 目标没有终点 | **根除**。所有目标都有终点，达成即止 |
| C3 目标与今天做什么无关 | **保留**（P2） |
| C4 建成后未被激活 | **保留**（P2，但优先级最高的那一项） |

## 3. 修订方案 v2

### 3.0 三个概念的边界（先立规矩）

| | 一句话定义 | 有终点 | 排期 | 与目标的关系 |
| --- | --- | --- | --- | --- |
| **任务** | 一次性要做完的一件事 | 有截止日 | **无**（不再有重复） | **服务于**某个目标 |
| **习惯** | 一个重复性动作 | 无 | **有**（每天 / 每周几 / 每周 N 次） | **服务于**某个目标 |
| **目标** | 一个长期的最终结果 | **有**（达成即止） | 无 | 包含"正在推进它的任务与习惯" |

三条推论：

1. **「每周 N 次」不是目标，是习惯。** 目标不承载任何周期口径。
2. **重复不是任务的属性。** 凡是"这件事会一直做下去"的，都建习惯；任务只管一次。
3. **任务是"做"，习惯是"保持"，目标是"到达"。** 三者不能互相替代，也不该互相计数。

### 3.1 目标：判据化，去掉计数与周口径

**3.1.1 目标类型：UI 不暴露，内部只按"判据"分，且只有两种**

`goals.goal_type` 列保留（同步、备份、历史数据都依赖它），但语义从"用户选的类型"改为"系统用的判据"。**只有两种判据**：

| 内部判据 | 用户看到的形态 | 进度从哪来 | 原类型 |
| --- | --- | --- | --- |
| `milestone` | 读完 21 本书 / 跑进 4 小时 / 体重 80 → 75 kg | 数值·次数判据：手动记录推进 | `quantity`、`change`、`custom`、`frequency`、`time` |
| `staged` | 读完 21 本书（拆 4 个阶段）/ 顺利完成毕业设计 | 阶段判据：勾选里程碑 | ——（复用已有的 `goal_milestones` 表） |

**「项目」不再是一种判据**（详见 3.1.2）。结论：

- 界面上**任何地方都不出现"目标类型"**（保持当前已删除的状态）。
- 目标表单只问两件事：**叫什么**、**做到什么程度算成**（数值·次数，或一组阶段）。
- migration 里做一次性归并：所有旧类型 → `milestone`；目标下若已有阶段清单则置为 `staged`。
- `frequency` 目标的历史数据不会错乱：它的 `goal_entries` 每条都带日期，累加起来就是历史总量，迁移后语义正确。

**3.1.2 「项目」和「目标」的区别：项目是范围，目标是判据**

这一条单独拎出来，因为**原方案里的"项目型目标"确实和项目重复**：

| | 项目 | 目标 |
| --- | --- | --- |
| 是什么 | **一组要做的事**（开题报告、文献综述、代码、答辩 PPT） | **一个要到达的结果**（顺利完成毕业设计并拿到学位） |
| 回答什么问题 | "这件事由哪些活儿构成" | "做到什么程度算成了" |
| 进度是什么 | 任务完成率（**已实现**，项目详情页已有进度条） | 判据达成度（阶段完成数 / 数值达到目标） |
| 有终点吗 | 不一定（"XX 客户跟进"可以永远开着） | **有**，达成即止 |

- 现状的"项目型目标"= **项目完成率的一个镜像**。这就是它显示成 `45%/1%` 的原因：它把"手段的完成度"当成了"结果的距离"，两者语义深度不同——**项目做到 90% 不等于离目标近 90%**（剩下那 10% 往往是最难的）。
- 而且**项目页本来就有进度条**（`ProjectsView.tsx` 的 `progress-bar`），目标里再放一个同源的进度是重复 UI。
- 因此：**项目降级为目标的关联对象**，出现在目标详情页「正在推进」里；需要"项目做完才算目标达成"时，用**阶段判据**表达（"开题通过 / 中期检查 / 定稿 / 答辩通过"），比 45% 精确得多。
- 项目与目标**不再有"类型"上的绑定关系**，只保留普通关联；`goals.project_id` 若无其它用途可一并清理（见 5 节）。

**3.1.3 删掉目标的「每周目标次数」**

- `goals.weekly_target` 列删除。
- 目标表单里那一格移除。
- 目标卡脚注不再出现"每周 N 次"。
- **这个概念整体迁移到习惯**（习惯本来就有 `target_per_week`，而且它是对的）。

**3.1.4 阶段清单：把"目标即里程碑"做成可操作的东西**

`goal_milestones` 表和数据层（建/改/删/查）**已经存在**，但成长页没有任何界面——这是一张"有表无界面"的表。新的目标模型正好把它激活：

- 目标详情页新增「阶段」区块：把大目标拆成 3–5 个可勾选的阶段。
  - 例：目标「读完 21 本书」→ 阶段「读完前 5 本」「读到第 10 本」「读完前 15 本」「全部读完」。
  - 例：目标「完成毕业设计」→ 阶段「开题通过」「中期检查」「论文定稿」「答辩通过」。
- 勾选阶段 → 该阶段标记完成（`goal_milestones.completed_at`）→ 生成一条成就（`achievements`，现有逻辑已支持）→ 目标进度前进。
- **目标的进度条按判据取值**（`resolveGoalProgress`，新单一真源）：
  1. 有阶段清单 → 进度 = 已完成阶段 / 总阶段；
  2. 否则是数值·次数判据 → 进度 = (当前值 − 起点) / (目标值 − 起点)。

**3.1.5 目标必须有终点**

- 目标达成 → 状态变 `completed`、生成成就、可归档。
- 归档后不再接受任何推进，入口收敛。
- 不再有"永远达不到"的目标类型（`frequency` 取消后，剩下的三种判据都能判定达成）。

### 3.2 习惯：接管重复能力

**3.2.1 排期模型**

`habits` 新增 `repeat_rule`（TEXT，JSON，沿用现有 `RepeatRule` 结构与 `parseRepeatRule`/`stringifyRepeatRule` 工具）。三种模式：

| 模式 | 内部表示 | 今日清单里 | "每周几次"从哪来 |
| --- | --- | --- | --- |
| **每天** | `{frequency:"daily"}` | 每天出现 | 派生 = 7 |
| **每周指定几天** | `{frequency:"weekly", weekdays:[1,3,5]}` | 只在指定的日子出现 | 派生 = 3（只读） |
| **每周 N 次（不指定日子）** | `null` | 每天出现，但提示"今天不用做也行" | 用户设置（现状） |

- 空值（`null`）= 现状行为，**已有习惯零影响**。
- 需要新增一个判定函数 `matchesRepeatRule(dateStr, rule): boolean`（现有 `repeat.ts` 全是"算下一次是哪天"，缺"这天该不该做"的判定）。
- 界面沿用现有的 `RepeatWeekdayPicker` 组件（周一排头的星期胶囊），**从任务表单搬到习惯表单**。

**3.2.2 今日清单只列今天该做的**

- `DayBoard` 的 `todayHabits` 过滤：规则的星期含今天，或规则为每天，或规则为空（浮动次数模式）。
- 浮动次数模式下，今日清单仍每天列出，但文案改为"本周 2/3 次 · 今天做不做都行"，避免制造"今天必须做"的错觉。
- 本周已满次数的浮动习惯，从清单顶部下沉到底部（与已完成任务同级）。

**3.2.3 「每周目标次数」的归属**

- 它是**习惯**的字段，保留。
- 在"每周指定几天"模式下变成只读派生值（= 选中的天数），不再让用户填两遍互相矛盾的数字。
- 在"每天"模式下派生为 7。

**3.2.4 「每月几号」不在本轮范围内 —— 它属于例行事务，不是习惯**

产品定位已明确：**任务 = 一个需要时间完成的事件**（不是一下就解决掉的）；**习惯 = 重复的、需要持续投入的动作**。据此：

- "交房租"这类**一下就解决、不需要时间完成**的例行事务，**既不是任务也不是习惯**。
- 它属于**日程/提醒**的范畴。而现状的提醒模块是**倒计时器与循环间隔提醒**（`timers` 表，`kind = 'interval' | 'task'`），**不是日历排程**——放不下"每月 1 号"。
- 结论：**决策 2 选 A**——习惯排期只做 **每天 / 每周几 / 每周 N 次**（周粒度），**不做 monthly**。
- 这也顺带简化了进度口径：习惯的进度永远是"本周 x/y 次"，不用再做"本月 x/y"这一套。
- **已知缺口（不在本轮解决）**："每月某天""每季度某天"的例行事务没有归宿。已在 §8 记录为未来「提醒/日程」改造的输入项。本轮**明说不覆盖**，不假装解决，也不做半吊子。

**推论**：任务删掉重复字段后，能力没有缺口——
- 需要"每天/每周"的持续投入 → 习惯；
- 需要"某天之前完成一件费时间的事" → 任务；
- 需要"每月某天交一次" → **提醒模块**（未来批次）。

### 3.4 三者关系：关联是"服务"，计量要显式声明

**3.4.1 关联分两种，区别在于"这个动作算不算目标的一个单位"**

任务/习惯关联目标，本质是"我正在为它做这件事"。但一个动作跟目标的关系有两种，必须分开：

| 关联类型 | 例子 | 完成/打卡后 |
| --- | --- | --- |
| **计量关联** | 目标「读完 21 本书」← 任务「读完《原则》」 | 目标 **+1 本**（真·计数） |
| **服务关联** | 目标「读完 21 本书」← 任务「整理读书笔记」<br>目标「读完 21 本书」← 习惯「每天读书 30 分钟」 | 目标数字**不动**，只出现在「正在推进」里 |

- 现状的 `goal_contribution`（任务/习惯各有一个"贡献值"）**已经在做这件事，但默认是"计数"**——所有关联都被当成加数，于是"整理笔记"这种明显不是"一本书"的动作也会给目标加 1。
- 新规则：**关联时显式选三态**，默认选"不计数"。
  - `不计数`（默认）→ 只作上下文，进「正在推进」
  - `算 1 个单位` → 完成/打卡时目标 +1
  - `算 N 个单位` → 目标 +N（保留现状的 contribution 能力，用于"一次推进 2 公里"这类）
- **目标侧决定它接不接受计量**：
  - 数值·次数判据的目标（「读完 21 本书」「累计 100 公里」）→ **接受**计量关联，完成就自动推进；
  - 阶段判据的目标（「顺利完成毕业设计」）→ **一律不计数**，阶段由用户勾选。
- 这样「读完 21 本书」照常自动前进，而「毕业设计」不会被任何无关任务污染。**两个诉求不冲突。**

**3.4.2 规则：同一个动作只能计量一个目标**

- 一个任务/习惯的"计量关联"**至多一个**。想在两个目标里都算数，只能选其中一个计量、另一个服务。
- 这一条直接消灭「同一件事记两遍」：没有双写口。
- 习惯默认**不计数**：习惯的单位是"次数/周"，与目标的单位（本书、公里、小时）不同源；只有当用户显式声明「这次打卡算 1 公里」时才计量。

**3.4.3 目标详情页「正在推进」区块**

用户第九条已认可。具体形态：

```
读完 21 本书                              进行中   12/21 本
  阶段
    ○ 读完前 5 本
    ○ 读到第 10 本
    ○ 读完前 15 本
    ○ 全部读完
  正在推进
    任务  读完《原则》第 3 章      今天到期     [算 1 本]
    任务  整理读书笔记              逾期 2 天    [服务]
    习惯  每天读书 30 分钟          每天 · 本周 5/7 次  [服务]
  [ 关联任务 ]  [ 关联习惯 ]  [ 记录进度 ]
```

- 关联任务：未完成优先，显示截止日与逾期状态，点击直达任务详情。
- 关联习惯：显示排期与本周进度。
- 方括号是**关联类型标记**（计量 / 服务），可在行内切换。
- 两个快捷入口：「关联任务」「关联习惯」——从这里把现有任务/习惯挂到目标上。
- 「记录进度」按钮 → 手动推进数值·次数判据（一次 +1，或手填当前值），用于没有可计量关联的时候。

**3.4.4 关联关系在其它页的呈现**

- 今日事项：行内目标徽标保留。计量关联显示"计入 X +1"，服务关联显示"服务于 X"——**徽标文案直接说明这次完成会不会算数**，用户不会再稀里糊涂。
- 习惯页：习惯卡同理由"计入 X +N"改为按关联类型显示。
- 成长页热点图：按目标筛选时，**该目标关联的任务完成数 + 关联习惯的打卡数**才点亮（这才是"按目标筛选投入强度"的正确口径）。
- 复盘页：「长期目标投入」改为**按判据的推进量**（阶段完成数 / 数值增量）；「精力投向 → 按目标」改为**按关联聚合任务 + 习惯打卡**，并标注构成。两块各司其职，不再同名不同义。

  > 目标「读完 21 本书」→ 拆 4 个阶段 → 关联习惯「每天读书 30 分钟」→ 从此每天的今日清单里，那条习惯都带着"服务于 读完 21 本书"的标记。

## 4. 决策记录

### 决策 1：关联要不要自动推进目标？—— **已解决：改为"显式计量声明"**

原方案给的三个选项（纯里程碑 / 有限自动 / 全自动）把"目标"和"计数"对立起来了，这个对立本身是错的。正确的切分不是**自动 vs 手动**，而是：

> **这个动作完成时，算不算目标的一个单位？**

- 目标「读完 21 本书」← 任务「读完《原则》」→ **算 1 本** → 完成后自动 +1（计数型目标照常自动前进）
- 目标「读完 21 本书」← 任务「整理读书笔记」→ **不算** → 只作上下文
- 目标「读完 21 本书」← 习惯「每天读书 30 分钟」→ **不算** → 只作上下文
- 目标「顺利完成毕业设计」（阶段判据）← 任何任务/习惯 → **一律不算** → 阶段由用户勾选

于是：

| 诉求 | 是否满足 |
| --- | --- |
| 「读 21 本书」应该是目标，且能自动前进 | ✅ 计量关联 |
| 目标不是计数器，不该被无关动作污染 | ✅ 默认"不计数"，阶段型目标全服务关联 |
| 同一件事不能记两遍 | ✅ 一个动作至多计量一个目标 |

**结论**：关联时选三态（`不计数` / `算 1 个单位` / `算 N 个单位`），默认 `不计数`；目标侧决定接不接受计量。详见 3.4。

### 决策 2：习惯排期要不要做 monthly？—— **已定：A，不做**

依据：任务 = 需要时间完成的事件；习惯 = 重复的持续投入。**"每月 1 号交房租"一下就解决、不需要时间完成，属例行事务，两边都不是** → 归**提醒/日程**范畴。

- 现状提醒模块是倒计时器与循环间隔提醒（`timers` 表），**不是日历排程**，放不下"每月 1 号" → **已知缺口，本轮不覆盖**，记入 §8 供未来「提醒/日程」改造。
- 习惯排期只做 **每天 / 每周几 / 每周 N 次**（周粒度）。顺带省掉"本月 x/y"这套进度口径。
- 任务删掉重复字段后能力无缺口：持续投入 → 习惯；某天前完成一件费时间的事 → 任务；每月某天交一次 → 提醒（未来）。

### 决策 3：项目型目标是否保留？—— **已定：删除，项目降级为关联对象**

理由见 3.1.2：项目型目标 = 项目完成率的镜像，语义深度不匹配（项目 90% ≠ 离目标近 90%），且项目页已有进度条、目标里再放一个同源的进度是重复 UI。目标改用**阶段判据**表达"这件事做成没有"，更精确。

- **`goal_type` 收敛为 `milestone` / `staged` 两种**；`goals.project_id` 一并清理（无其它用途）。
- 历史 `project` 型目标按"起点 0、目标 100、单位 %"折算，或直接转成阶段判据——**在 migration v22 中处理**。

| `goals.goal_type='project'` 的历史目标 | 按"起点 0、目标 100、单位 %"折算，其余类型的起止值不动 |
| `tasks.goal_contribution` / `habits.goal_contribution` | 全部置 **0**（用户从未显式声明过"这个算一个单位"） |
| `goal_entries` | 把历史 `source_type='task'/'habit'` 的记录**按目标合并为一条 `manual` 记录**（值 = 该目标历史总和），保证 `current_value` 不变、且之后不再被动变化 |
| `tasks` | 若存在带重复规则的任务 → 转成对应习惯后再清列 |
| `habits` | 保持不变（`repeat_rule` 为空即旧行为） |

**同步（`docs/ARCHITECTURE.md` §7bis 三处一致）**

1. `src/lib/sync/tables.ts` — 表集合不变（`goal_entries` 仍在范围内）。
2. `src/lib/sync/columns.ts` — `habits` 加 `repeat_rule`；`tasks` 去 `repeat_rule`；`goals` 去 `weekly_target`（及 `project_id`，依赖决策 3）。
3. `src-tauri/src/lib.rs` — migration v22 + 确认 `trg_habits_upd` / `trg_tasks_upd` 触发器覆盖新列与删列。
4. `SYNC_SCHEMA_VERSION` 9 → **10**；旧端按 header 闸门整体拒收并提示升级，升级顺序无关。

**备份（`src/lib/db/backup.ts`）**

- `habits` 插入语句加 `repeat_rule`；`tasks` 去掉 `repeat_rule`；`goals` 去掉 `weekly_target`。
- `goalEntries` 仍全量导出（保证老备份能导入）。

## 6. 落地顺序

| 批次 | 内容 | 动 schema | 风险 |

## 8. 附录：本次修订未覆盖的部分

- **未做真机验证**：涉及界面的项建议在桌面与 Android 双端各验一遍；Android 端需同步改 `src/components/mobile/TaskActionSheet.tsx`。
- **性能**：习惯排期过滤发生在前端内存（`habits` 全量已在 store 中），不新增查询；目标「正在推进」同样走现有 store 数据。无新增 SQL 压力。
- **子任务 / 标签 / 项目**：本次不涉及。它们与目标的关系同属"服务关系"，可在后续批次对齐。
- **同步冲突**：`goal_entries` 的值域收窄（不再有 task/habit 来源）意味着两端对同一条 `source_type` 的理解必须一致——靠 `SYNC_SCHEMA_VERSION` 闸门保证：旧端拉到新日志整体拒收并提示升级，不会静默误解。
- **已知缺口 · 例行事务无归宿（决策 2 遗留）**："每月 1 号交房租""每季度报税"这类**一下就解决、不需要时间完成**的例行事务，在本轮**没有位置**：
  - 现状提醒模块是倒计时器与循环间隔提醒（`timers` 表，`kind = 'interval' | 'task'`），**不是日历排程**，放不下"每月某天"；
  - 本轮不为此新建数据结构，也不做半吊子；
  - 建议在**未来「提醒/日程」改造**（把提醒从倒计时器升级为带日期的排程）时一并解决，届时的模型应是：重复 + 固定日期 + 到期推送，与习惯的"持续投入"语义区分开。
- **子任务 / 标签 / 项目**：本轮不涉及。它们与目标的关系同属"服务/关联"，可在后续批次对齐；项目型目标删除后，项目在目标页的位置由「正在推进」里的关联体现。

**顺带修掉的两个真 bug**（写回归测试时才暴露）：

1. 项目型目标只要有进度就被判成"已完成"——旧口径拿 `target_value`（默认 1）当分母，`50 >= 1` 成立。
2. 频率型目标的周次数把任务完成也算进分子，而分母只算习惯——一次行动记两遍，显示 `5/3`。
