## 1. 一句话结论

核心两条主干流程（任务执行、账本记录）已经成熟到可日常依赖，本地优先与数据安全设计明显优于同类工具。v1.3.0 已完成第一轮修补：复盘口径修复、README 与死字段对齐、全局搜索、目标-习惯-任务-复盘闭环。当前剩余问题集中在四处：**账本录入效率与查询能力不足、同步链路的单点与韧性、热点模块的迭代成本、零使用功能（成就、计时/倒计时、纪念日、附件）的取舍**。

## 3. 功能设计做得好的地方

1. **本地优先架构扎实**：数据全部落在本机 SQLite，无账号、无云依赖，隐私与离线可用性成立；Windows 与 Android 共用同一份前端代码，维护成本低。
2. **数据安全网完整**：SQLite 快照 + JSON 备份 + 自动备份 + 回收站（软删除）+ 同步前冲突检测，误操作恢复路径清晰，这在个人工具里属于超出平均水准的设计。
3. **分层纪律好**：领域规则下沉到 `src/lib/` 纯函数（可单测），组件不直接写 SQL，db 层不掺业务判断，测试覆盖到 181 个用例；这是项目能持续迭代的基础。
4. **提醒走操作系统层**：`src-tauri/src/os_reminders.rs` 让提醒在应用退出后仍生效，比"前端定时器"方案可靠得多。
5. **双端同步方案克制**：飞书云盘 JSONL 日志 + HLC 合并、无自建服务器，用最小成本换到跨设备一致性；同步表/列在 `src/lib/sync/tables.ts`、`src/lib/sync/columns.ts` 集中约定，便于审查。

## 4. 不足与可以完善的地方

### P1：效率问题

#### P1-1 账本录入效率与查询能力不足

- **现象**：无筛选、无搜索、无周期记账、无账户余额与转账、无分类预算；快捷金额固定为 10/20/50/100，与真实支出分布（97/104 笔低于 ¥50，均值 ¥23.61）不匹配；约 30% 记录为事后回填，备注平均仅 2.28 字符。
- **证据**：账本视图与 `src/lib/db/` 账本域的现有能力；使用数据的金额分布与回填比例。
- **影响**：高频入口的操作成本直接决定数据质量——回填多、备注空，导致月度复盘只能看到总额，看不到结构。
- **建议**：快捷金额改为按历史频次自适应 + 保留自定义；增加"重复上一笔"、日期快捷（今天/昨天/前天）、最近金额；列表增加分类/账户/日期范围筛选与关键字搜索；引入周期账单与分类预算。

### P2：可持续性与工程问题

#### P2-1 同步链路单点与韧性

- **现象**：同步只支持飞书云盘一条通道；冲突以检测为主，处置过程对用户可见性有限；JSONL 日志只追加不压缩；凭据存储方式需要加固。
- **影响**：通道故障或凭据失效即同步中断；日志长期膨胀会拖慢启动与合并；用户遇到冲突时缺少明确的操作指引。
- **建议**：冲突列表化与可回滚呈现；日志压缩/快照；凭据改用系统密钥链（Tauri 插件）；评估增加 WebDAV 等第二通道。

#### P2-2 大文件热点

- **现象**：`src/store/app.ts`（747 行单 store）、`src/lib/db/tasks.ts`、`src-tauri/src/lib.rs` 集中了过多职责。
- **影响**：每次改动的回归面偏大，评审与测试成本随版本线性上升。
- **建议**：按域拆分 store 切片与 db 模块，Rust 侧按 command 分组；先加测试再拆，避免行为漂移。

#### P2-3 功能面与使用面的落差

- **现象**：成就、计时/倒计时、纪念日、附件、目标里程碑等功能建成但零使用；任务平均 4.67 次编辑说明创建表单与真实输入节奏不匹配。
- **影响**：维护成本持续投入在无人使用的路径上，而高频路径（任务创建、账本录入、检索）体验未优化。
- **建议**：对零使用功能做取舍——要么在首启引导/今日页给出自然的使用场景（如"纪念日"在今日页显示），要么评估下线；创建任务默认只保留标题/日期，其余字段渐进展开。

## 5. 改进顺序

| 优先级 | 事项 | 目标 | 主要改动点 | 验收 |
| --- | --- | --- | --- | --- |
| P1 | 账本录入提速 | 提高实时记账率与数据质量 | 自适应快捷金额、重复上一笔、日期快捷、筛选与搜索、周期账单 | 回填占比下降；备注平均长度上升 |
| P2 | 同步加固 | 降低单点故障与冲突成本 | 冲突可视化、日志压缩、密钥链存凭据、可选 WebDAV | 断网/换机/冲突场景可恢复且步骤明确 |
| P2 | 拆分热点模块 | 控制迭代成本 | `src/store/app.ts`、`src/lib/db/tasks.ts`、`src-tauri/src/lib.rs` | 拆分后测试全绿，行为无变化 |
| P2 | 零使用功能取舍 | 收敛维护面 | 首启引导或下线评估（成就、计时、纪念日、附件） | 每个功能有明确入口与使用场景，或退出代码库 |

### 建议的版本节奏

1. **v1.4（效率）**：账本录入提速（P1-1），先解决高频入口的数据质量。
2. **v1.5（韧性）**：同步加固与冲突呈现（P2-1）。
3. **v2.0（结构）**：热点模块拆分，同步引入第二通道评估（P2-2）。
4. **零使用功能取舍（P2-3）**：不绑定版本，按模块逐个决定给入口还是下线。

## 6. 附录：数据口径与分析方法

- **数据来源**：本机 `%APPDATA%\com.yunshan.yield\app.db`。分析时将数据库连同 WAL/SHM 复制到临时目录后只读访问，原库未做任何修改；`PRAGMA integrity_check` 通过。
- **统计区间**：2026-09-14 ～ 2026-10-18。
- **口径定义**：延期完成 = `status = completed` 且 `completed_at` 所在本地日期晚于 `due_date`；单任务时长 = 开始时间到结束时间；任务编辑事件 = `task_events` 记录数。
- **已知局限**：① 单人单机样本，不能代表全部用户；② 无埋点数据，"未使用"可能是入口不可达，也可能是需求不存在，需结合访谈验证；③ 数据窗口约 5 周，长周期习惯（如月度目标、纪念日）天然偏低，解读时需打折。
- **复现验证命令**：`npx tsc -b`、`npx vitest run`、`npx vite build`、`npm run release:check`。
